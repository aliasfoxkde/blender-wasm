# Audit 2026-08-07: Blender WASM Recovery

## Bottom Line

The previous AI did not finish the MVP. It made several useful cleanup changes, but it also created false progress:

- It copied or generated tiny placeholder files named `blender.js` and `blender.wasm`.
- It added `artifacts/smoke_test.c`, which hard-codes a fake Blender version string.
- It added a runtime wrapper but did not wire the viewport to it until this audit.
- It added Playwright tests that only prove the page loads, not that Blender or Blender-derived code runs.
- It documented a plausible build direction, but some of the technical claims need to be verified against actual Blender CMake behavior and logs before implementation.

The project is now in a better TypeScript/lint state than before, but the central product problem remains unsolved: there is still no verified Blender-derived WASM artifact loaded by the browser.

## Remediated Baseline

After this audit, the fake public Blender artifacts were removed. The expected baseline state is:

- `public/wasm/blender/blender.js` is absent.
- `public/wasm/blender/blender.wasm` is absent.
- `public/wasm/blender/README.md` explains what valid artifacts are.
- `pnpm audit:wasm` passes only because no public Blender artifact is installed.
- The app enters the Blender view and reports a clear missing-artifact error.

This is intentional. An honest missing-artifact baseline is better than a fake artifact that appears to work.

## What Improved

3. `pnpm test:run` exits 0.

5. The runtime registry was reduced from fake subsystem modules to one `blender` artifact.

## What Is Still Wrong

### 1. The Current WASM Artifact Is Fake

Evidence:

- `public/wasm/blender/blender.wasm` is 874 bytes.
- `artifacts/blender-wasm/blender.wasm` is 975 bytes.
- `artifacts/smoke_test.c` contains:

```c
const char* bw_get_version_json(void) {
    return "{\"version\": \"4.2.0-emscripten\", \"buildDate\": \"2026-08-07\", \"compiler\": \"Emscripten\"}";
}

int bw_run_smoke_test(void) {
    return 0;
}
```

That is not Blender source. It is a hard-coded string.

The new command catches this:

```bash
pnpm audit:wasm
```

Expected current result:

```text
FAIL: WASM is under 1 MiB. This is almost certainly not Blender-derived output.
```

Do not mark the MVP complete while `pnpm audit:wasm` fails.

### 2. The App Was Loading Through The Wrong Runtime Path

Before this audit, `BlenderViewport.tsx` called:

```ts
moduleManager.load('blender')
```

That goes through `WASMLoader`, which calls `WebAssembly.instantiate()` on `info.url`.

But `info.url` is `/wasm/blender/blender.js`, not raw WASM. That is a mismatch.

This audit changed `BlenderViewport.tsx` to call:

```ts
await blenderRuntime.load({ canvas: canvasRef });
const smokeResult = await blenderRuntime.runSmokeTest();
```

That is the correct architectural direction.

### 3. The Emscripten Wrapper May Still Not Match The Generated JS

`EmscriptenBlenderRuntime.ts` expects a global factory:

```ts
CreateBlenderWasmModule
```

The current generated `public/wasm/blender/blender.js` does not appear to expose that factory. It looks like a non-modularized Emscripten shell that defines `var Module = ...` and exports only `main`.

Required rebuild flags for the MVP artifact:

```bash
-sMODULARIZE=1
-sEXPORT_NAME=CreateBlenderWasmModule
-sEXPORTED_FUNCTIONS=_bw_get_version_json,_bw_run_smoke_test,_malloc,_free
-sEXPORTED_RUNTIME_METHODS=ccall,cwrap,UTF8ToString
-sALLOW_MEMORY_GROWTH=1
```

Do not patch the TypeScript runtime around a bad artifact. Rebuild the artifact correctly.

### 4. The Playwright Test Does Not Prove Blender Runs

`tests/e2e/blender-smoke.spec.ts` currently verifies:

- page loads
- title exists
- splash/dashboard exists
- body can be clicked

It does not click `New Project`.
It does not enter the Blender viewport.
It does not assert `data-testid="blender-smoke-status"`.
It does not fail when the runtime fails to load.

This is why `pnpm test:e2e` passed while the browser console showed:

```text
Failed to load Blender: RangeError: WebAssembly.Memory(): Property 'maximum': value 131072 is above the upper bound 65536
```

Future e2e tests must fail on browser console errors and must exercise the Blender runtime path.

### 5. The Build Roadmap Contains Unverified Claims

`docs/BLENDER_WASM_ROADMAP.md` says CMake configure succeeds and individual static libraries build. That may be true, but the current repo does not include the supporting logs under `artifacts/logs/`.

Before using that roadmap as fact, require:

- `artifacts/logs/configure.log`
- `artifacts/logs/build.log`
- `artifacts/logs/ninja-targets.txt`
- exact commands used
- exact first failing compiler/linker/CMake error

## Immediate Recovery Recommendation

Do not ask the cheap AI to "finish the MVP".

Ask it to do one narrow, falsifiable thing:

```text
Make ./scripts/build-blender-wasm.sh configure produce artifacts/logs/configure.log and exit 0 from a clean Docker volume. Do not create or modify public/wasm/blender/*. Do not create fake smoke-test artifacts. Stop after configure passes and paste the first 80 and last 120 lines of the configure log into docs/build-notes/001-configure.md.
```

After configure is trustworthy, the next task is:

```text
Run ninja -t targets all inside the configured build and save the output to artifacts/logs/ninja-targets.txt. Identify the smallest Blender source static library target that can compile to wasm32 without GHOST, Python, Cycles, or GPU draw engines. Do not link a final browser artifact yet.
```
